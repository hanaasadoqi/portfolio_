## Introduction

In my previous posts, I covered how I organized the file structure for my Next.js portfolio rebuild and the decisions I made to ensure scalability and maintainability. Now that the foundational pieces are in place, it’s time to tackle the next major challenge: styling.

In the initial build of my portfolio, I made the rookie mistake of mixing too many styling approaches—TailwindCSS, SCSS, CSS modules, and even some plain CSS thrown in for good measure. This led to inconsistent styles across the site, with no clear structure, making it increasingly difficult to ensure visual consistency.

To clean this up, I'm focusing on:

- Consolidating my styling with TailwindCSS for consistency.
- Using SCSS only where necessary, particularly for dynamic CSS variables.
- Fixing semantic HTML issues by using proper tag structures, which not only improves maintainability but also enhances accessibility.

If you’re working through a similar challenge in your project, this guide should help you avoid some of the pitfalls I encountered. Now, let’s dive into how I’m cleaning up my styling and making it future-proof.

## The Mistake: Mixing Too Many Styling Approaches

When I first started working on my portfolio, I was excited by the range of styling options Next.js provides. Between **Global CSS**, **CSS Modules**, **TailwindCSS**, and **Sass (SCSS)**, I saw all the potential and ended up mixing them all, thinking I could get the best of each.

In theory, this combination sounds powerful:

- **Global CSS**: A traditional styling approach where you define global styles that affect the entire application. While this is easy to implement, it can lead to **larger CSS bundles** and affect performance if not scoped carefully.
- **CSS Modules**: Scoped CSS that avoids naming conflicts and makes it easier to manage local styles. It works particularly well for **component-level** styling.
- **TailwindCSS**: A utility-first CSS framework that allows for inline utility classes in your JSX. It’s quick and offers responsive design out-of-the-box.
- **Sass (SCSS)**: A preprocessor that adds powerful features like **variables**, **mixins**, and **loops**, making CSS more dynamic and reusable.
- **CSS-in-JS**: Styles embedded directly within JavaScript components, useful for **dynamic** or **theme-based** styles.

But in reality, this turned into a tangled mess. By mixing too many different approaches, I created a fragmented and inconsistent design system. Styles were scattered, difficult to maintain, and even worse, some styles were being overwritten or duplicated, leading to unnecessary bloat in the CSS output.  Worse, I found myself overriding base HTML tags like `h3` to look like `h4` or `h5`, which further impacted both performance and accessibility.

It was clear I needed a better approach—a strategy that consolidates styling methods, reduces duplication, and improves maintainability across the board.

## The Solution

### Rule #1: Consolidate with TailwindCSS for Consistency

TailwindCSS is incredibly powerful for creating utility-first designs directly in your `jsx` components. However, using it consistently across the entire project can become a challenge without a solid strategy to manage your styles effectively.

#### Refactor Plan

- **Remove unnecessary custom CSS and CSS modules**, and replace them with Tailwind's utility classes wherever applicable. This helps to reduce duplication and makes your styling approach much more consistent.
- **Use Tailwind's `@apply` directive** to define commonly used styles for reusable components like buttons and cards.
  ```css
      .btn-primary {
        @apply bg-blue-500 text-white px-4 py-2 rounded;
      }
    
    ```

This reduces the need for hardcoding styles repeatedly across components, making your code DRY (Don't Repeat Yourself).

Leverage Tailwind's responsive utilities consistently across the project to ensure the site adapts fluidly to different screen sizes, providing a seamless UI experience for users on any device.

By consolidating most of the styling within TailwindCSS, I hope to eliminate the confusion caused by mixing methods and set a clear, maintainable styling direction.

---

### Rule #2: Use SCSS for Dynamic Variables Only

While TailwindCSS is great, there are still cases where dynamic CSS variables can be useful, especially for things like themes or breakpoints that need to be calculated or modified at runtime. Luckily, this is exactly what I need to solve my aforementioed problem!

#### Refactor Plan

- **Limit SCSS usage** to dynamic variables, letting Tailwind handle the rest. By keeping SCSS focused, TailwindCSS remains the backbone of the styling, while SCSS steps in when flexibility is needed.
  - The best part is that SCSS is prerendered at build time so that means that by the time TailwindCSS runs at build time, our CSS variables will already have been defined.
- Define **theme variables** in SCSS, like primary colors or font sizes, and inject them as CSS variables. This way, everything is precomputed by the time Tailwind kicks in.
  ```scss
    $primary-color: #3490dc;
    :root {
      --primary-color: #{$primary-color};
    }
    ```
- You can then use TailwindCSS to define utilities based on CSS variables; since these utilities will be equal to the defined CSS variables, when their values change, so do the values of the utilities -- without having to recompile the TailwindCSS code like you would with hardcoded data.
  - In your `tailwind.config.ts`:
    ```ts
      theme: {
        extend: {
          colors: {
            primary: 'var(--primary-color)',
          }
        }
      }
      ```

If your site needs to dynamically switch themes (e.g. dark mode vs. light mode or my own styling plan), you can use SCSS to manage your dynamic variables and apply them globally or however you need to to satisfy your application's needs

### Rule #3: Fix Semantic HTML and Stop Overriding Tags

In my first version, I was guilty of forcing tags like `h3` to behave like `h4` or `h5`, which not only cluttered the code but also wrecked the site's **semantic structure**. This made everything harder to maintain and less accessible for users and search engines.

#### Refactor Plan

- **Use the correct HTML tags**: Stick to the right tag for the right content. If you need an `h4`, use it. Avoid overriding tags (e.g. styling `h3` to look like an `h4`) to maintain clear, semantic structure.
  - All elements should follow **semantic HTML** guidelines.
- **Use Tailwind’s typography utilities** (`text-lg`, `font-bold`, etc.) to manage typography without directly altering HTML tags to ensure they maintain their correct semantic meaning.
- **Predefine base styles for HTML tags** using Tailwind's `@apply` directive, making sure they are consistent, responsive, and adaptable to the theme.
  - For more granular control (like specific styles in different sections), I’ll define those in individual component files (e.g., `AboutCard`, `SkillCard`) so I can easily handle variations without compromising the overall structure.

#### Why This Matters

- **Accessibility**: Proper tags mean screen readers and assistive technologies can interpret the site correctly, improving user experience for everyone.
- **Maintainability**: Clean, well-structured HTML makes it easier to track styles, avoids unnecessary CSS overrides, and makes it easier to understand and maintain your codebase, especially as the project grows.
- **SEO**: Search engines

---

### Rule #4: Never Skip Responsive Design and Testing

TailwindCSS’s responsive utilities make handling responsive design straightforward, but just relying on that isn't enough. Testing is critical to ensure your layout looks solid across all screen sizes and devices.

#### Refactor Plan

- **Mobile-first design**: Tailwind is mobile-first by default, which means all components should scale well from small screens upwards. I’ll test across key breakpoints (`sm`, `md`, `lg`, `xl`) to ensure consistency and avoid any awkward layout shifts.
- **Cross-browser and device testing**: It’s not enough for it to look good on just one browser or device. Tools like **BrowserStack** and **Sauce Labs** are essential to ensure everything works seamlessly across all platforms and screen sizes—because nobody wants a layout that breaks on Safari or a weird screen resolution.

#### Why It Matters

- **User Experience**: Consistent layouts across devices and browsers mean a smoother experience for your users, and better user experience leads to higher engagement.
- **Preventing headaches later**: Responsive design isn’t just for looks—poor responsiveness leads to unpredictable bugs that could surface as users navigate your site, which you’d rather catch early on.

## Using Semantic HTML for Accessibility and Structure

### Full-Screen Sections

#### Definition

Section elements, defined by the `<section>` tag, are block-level elements used to group content into thematic areas. Each section should be logically related, representing a specific purpose or theme. These sections also serve to clearly divide content in a webpage for accessibility and improved UX, as they are recognized by screen readers, enabling easier navigation for users with disabilities.

#### Characteristics

- **Block-level** element.
- Used to **group thematic content**.
- Can contain **headings, paragraphs, lists, media, and other block-level elements.**

#### When to Use

- **Block-level element**: Meaning it takes up the full width available and starts on a new line.
- Used to **group thematically related content.**
- **Adds semantic value**: It gives meaning to your content structure, making it easier for search engines and assistive technology to understand.
- **Alternatives:** `div` (layout), `<article>`, `<nav>`, or `<aside>`.

#### Usage

- Use a `<section>` when grouping logically related content, such as a **product category, contact form, or gallery of images.**
- Creates a *clear division for screen readers*, improving accessibility and UX by separating content
  ```html
      <section class="min-h-screen flex items-center justify-center">
        <h1 class="text-5xl font-bold">Welcome</h1>
      </section>
    ```
- Use for content with *multiple headings or logical parts*; each with its own subheading.
- **Do not use for purely visual/layout purposes.** For layout-only needs, use a non-semantic `<div>` instead.
- **Examples**
  - features, testimonials, or services within a web page.
  - dashboard panel, settings, etc.

For my portfolio, especially because it's intended to be rendered on a single route, `<section>`s are crucial to my refactor plan. Wrap major sections like `Hero`, `About`, and `Skills` in `<section>` tags.

#### Best Practices

- **Avoid overusing sections**, especially for purely visual purposes; use **only for semantically grouped content.**
- Each section should contain a **heading tag to define the start of its content (`<h1>` to `<h6>`).***
- **Use `min-h-screen` for full-screen height** to ensure each spans the entire viewport.
- Flex utilities (`flex items-center justify-center`) **ensure the content remains vertically and horizontally centered** within each section.

### Articles for Blogs and Case Studies

#### Definiton

The `<article>` element is used to represent **self-contained, independent content** that could stand on its own or be reused. This tag is **ideal for blog posts, case studies, or user-generated content** like reviews or forum posts. If you can imagine the content being syndicated (e.g., in an RSS feed), then it likely belongs in an `<article>`.

#### Characteristics

- **Block-level element.**
- Represents **stand-alone, self-contained content** that makes sense on its own.
- Often paired with semantic elements such as `header`, `footer`, and `section`.

#### When to Use

- Used for **posts, articles, news, and user-generated content.**
- Content can be **read independently or shared** in a distributed or syndicated context.
- **Do not use if it doesn't have a standalone meaning separate from the page.**

#### Usage

- Use `<article>` for blog posts or case studies where each unit of content is a **self-contained entity.**
  - Blog posts
  - News articles
  - Product reviews
  - Case studies
- Helps search engines recognize content as distinct and improves SEO by allowing search engines to accurately interpret its structure.
  ```html
    <article class="mb-8">
      <h2 class="text-3xl font-semibold">Understanding Component-Driven Design</h2>
      <p>In this blog, I plan to...</p>
      </article>
      ```
- Avoid using `<article>` for content that **doesn't make sense when separated** from the page context.

#### Common Use Cases

The `<article>` tags allow you to build modular, independent content blocks.

##### **Blog Post**

```html
  <article>
    <h1>How to Build a React App</h1>
    <p>This guide walks you through building a React app from scratch...</p>
    <p>By the end, you will have a basic understanding of JSX, components, and state management...</p>
  </article>
  ```

##### **News Story**

```html
  <article>
    <h1>Latest News on Climate Change</h1>
    <p>Global temperatures are rising faster than anticipated, experts say...</p>
    <p><time datetime="2024-10-02">October 2, 2024</time></p>
  </article>
  ```

##### **Forum Post**

```html
  <article>
    <h1>My Journey Learning JavaScript</h1>
    <p>I started learning JavaScript a few months ago, and here’s what I’ve learned so far...</p>
    <p>By: <em>User123</em></p>
  </article>
  ```

#### Best Practices

- Ensure proper keyboard navigation and interaction for interactive elements within the article.
- When properly nested with `<header>`, `<footer>`, and correct heading tags, it can help improve how its content is indexed on Google.
- **Combine with other semantic tags:**
  - `header` for article titles.
  - `footer` for bylines, author names, or dates.
  - `section` to subdivide large articles.
- Always use heading elements (`<h1>`, `<h2>`, etc.) inside an article to organize the content logically.
  ```html
    <article class="mb-8">
      <header>
        <h2 class="text-3xl font-semibold">Understanding Component-Driven Design</h2>
        <time datetime="2024-09-30">Published on September 30, 2024</time>
      </header>
      <p>Component-Driven Design (CDD) is an approach to building UIs where each part of the interface is broken down into reusable, isolated components...</p>
      <footer>
        <p>Written by John Doe</p>
      </footer>
    </article>
    ```

#### Stylng

Can be styled like any other block element with margins, padding, borders, etc.

```css
  article {
    padding: 20px;
    border: 1px solid #ccc;
    margin-bottom: 20px;
    background-color: #fafafa;
  }
  ```

### Figures for Images and Videos

#### Definition

Semantic tags **used to encapsulate media**, such as images, charts, or code snippets, along with an optional caption provided by the `<figcaption`>` element. This element **provides a semantic wrapper for media and its description**, enhancing both accessibility and readability.

#### Characteristics

- **Block-level** element.
- Used to **associate media content** with a caption.
- The `<figcaption>` tag is **optional**; commonly **used to describe content**.

#### When to Use

- Use when you need to **associate a description with a visual element**, such as an image, chart, or diagram.
- Use when media content is an **important part of the document and makes sense independently** (rather than merely a decorative element).
- **Do not use if the content is purely structural.**

#### Usage

- Use `<figure>` to wrap content such as images and videos and provide proper descriptions using `<figcaption>`.
- Improves accessibility by associating captions with media content.
  ```html
    <figure class="max-w-md mx-auto py-8">
      <img srrc="image.jpg" alt="Image">
      <figcaption class="text-center text-sm text-gray-500">Portfolio Project</figcaption>
    </figure>
    ```

#### Common Use Cases

##### **Image with a Caption**

```html
  <figure>
    <img src="landscape.jpg" alt="A beautiful mountain landscape">
    <figcaption>A view of the Rocky Mountains during sunset.</figcaption>
  </figure>
  ```

##### **Diagram with a Caption**

```html
  <figure>
    <img src="flowchart.png" alt="Flowchart of the application architecture">
    <figcaption>Application architecture flowchart.</figcaption>
  </figure>
  ```

##### **Code Snippet with a Caption**

```html
  <figure>
    <pre><code>console.log("Hello, World!");</code></pre>
    <figcaption>A basic JavaScript example of a console log statement.</figcaption>
  </figure>
  ```

#### Best Practices

- **Always include `alt` attribute for images** inside `<figiure>`.
  - Provides a **description of the image** itself.
  - `<figcaption>` is used to **provide additional context or commentary.**
- **Use `<figcaption>` to provide details or context** for media that aren't immediately obvious from the image or media itself.
  - **Always include to improve the overall semantic structure**; helps search engines index images and other media content more accurately.
- **Don't use for decorative elements**; reserve for content that is important to the page.

#### Styling

Use CSS to add padding, margins, and borders to create a visually appealing layout.
```css
figure {
  margin: 20px 0;
  text-align: center;
}

figcaption {
  font-size: 14px;
  color: #555;
  margin-top: 5px;
}
```

### Interactive Elements (Buttons, Inputs, Forms)

#### Definition

Interactive elements like `<button>`, `<input>`, and `<form>` **allow users to interact with your site** — whether by submitting data, navigating, or triggering events. These elements are **fundamental for user engagement and form submission.**

#### Usage

Interactive elements **should be used with proper semantic structure and accessibility in mind** to ensure that your forms and buttons are usable by everyone.
```html
  <form action="/submit" method="POST" class="space-y-4">
    <label for="name">Your Name:</label>
    <input type="text" id="name" name="name" class="input-primary" required>
    <button type="submit" class="btn-primary">Submit</button>
  </form>
  ```

#### Best Practices

- **Use semantic elements**: Use `<button>`, `<input>`, and `<form>` correctly to ensure accessibility and ease of use.
- **Label your inputs**: **Always provide `<label>` elements** for inputs to make forms accessible.
- **Use the correct type attribute** for buttons (submit, reset, button) to avoid unexpected behavior.
  - `type="button"` for generic actions.
  - `type="submit"` to submit a form.
  - `type="reset"` to reset a form’s fields to default values.
- **Accessible button labels**: If using *icon-only buttons*, make sure to **use `aria-label` to provide context** for screen readers.
- **Use placeholder sparingly**: Don’t rely solely on placeholders to communicate an input’s purpose, as they disappear once the user begins typing. **Always pair inputs with labels.**
- **Use the correct method**: Typically, use *`method="POST"` for sensitive data (like login forms)* and *`method="GET"` for non-sensitive data (like search forms)*.
- **Group related inputs logically**: Use `<fieldset>` to group related inputs and `<legend>` to label them.
  ```html
    <fieldset>
      <legend>Personal Information</legend>
      <label for="name">Name:</label>
      <input type="text" id="name" name="name" required>

      <label for="email">Email:</label>
      <input type="email" id="email" name="email" required>
    </fieldset>
    ```

#### Common Mistakes

- **Forgetting labels**: Inputs without labels can confuse users, especially those relying on assistive technologies.
- **Overcomplicating forms**: Keep your forms simple and functional to avoid frustrating users.
- **Leaving out the `type` attribute**: Omitting this **can cause unwanted behavior in forms**, especially if the button defaults to submit.
- **Ignoring input validation**: HTML5 provides built-in form validation using attributes like `required`, `minlength`, and `maxlength`.
- **Not using `action` and `method`**: These attributes define how the form is processed. **Omitting them can break form functionality.**

#### Usage

Use `<button>`, `<input>`, and other form elements appropriately to ensure accessibility.

- Semantic HTML ensures that assistive technologies can interact with your forms correctly.
  ```html
    <form action="/submit" method="POST" class="flex flex-col space-y-4">
      <input type="text" class="input-primary" placeholder="Your Name">
      <button type="submit" class="btn-primary">Submit</button>
    <form>
    ```

##### Common Use Cases

- **Forms**: Collect user input (e.g., contact forms, sign-up forms).
- **Buttons**: Trigger actions, submit forms, or initiate an event (e.g., form submission, loading additional content).
- **Input Fields**: Collect various types of user data such as text, emails, passwords, dates, and numbers.

#### Definition

Typography elements like headings (`<h1>` to `<h6>`), paragraphs (`<p>`), and inline text formatting elements such as `<strong>`, `<em>`, and `<span>`, **help structure your content and define the visual hierarchy of your text**. Good typography is *essential* for **readability, accessibility, and user engagement.**

Use Tailwind to apply typography consistently across HTML elements, including headings, paragraphs, lists, etc.

<InfoBlock>

### What is Autoprefixer?

Autoprefixer is a PostCSS plugin that adds vendor prefixes to your CSS. It's essential for ensuring that your CSS works across different browsers that require specific prefixes for certain features—especially as newer CSS features get rolled out inconsistently across browsers.

#### Why Use Autoprefixer?

Browser compatibility can be tricky. As CSS evolves, some browsers might not fully support newer features, or they might need vendor-specific prefixes to render them correctly. That’s where Autoprefixer comes in.

Autoprefixer takes care of adding these browser-specific prefixes based on usage statistics, so you don’t have to worry about manually adding them for each property.

**Example**:

```css

  /* Autoprefixer automatically adds vendor prefixes */
  display: flex;
  /* Output for Safari or older browsers might look like: */
  -webkit-display: flex;

```

### Adding Autoprefixer to Your Project

Install the package with the following:

```bash

  npm install autoprefixer --save-dev

```

Update your `postcss.config.mjs` to include Autoprefixer:

```js

  /** @type {import('postcss-load-config').Config} */
  const config = {
    plugins: {
      tailwindcss: {},
      autoprefixer: {},
    },
  };
  export default config;

```

#### Why This Is Important

While most modern browsers can handle CSS without prefixes, some older versions still require them. Autoprefixer ensures cross-browser reliability and helps avoid frustrating compatibility issues, especially when using newer CSS properties.

<Callout> **Pro Tip**: While Autoprefixer can be very useful, **you don’t necessarily need a preprocessor** unless you plan to write a lot of custom CSS. </Callout>

</InfoBlock>

### Importing TailwindCSS Directives

Before we dive into the base styles, let's ensure that TailwindCSS is correctly set up by importing its core directives into your CSS file. These directives will inject Tailwind's default styles into your project.

To import Tailwind into your main CSS file (typically `globals.css` or `styles.css`):

```css  
  @tailwind base;
  @tailwind components;
  @tailwind utilities;

  ```

#### What These Directives Do

- **`@tailwind base`**: Injects Tailwind's Preflight base styles (which we'll cover in a moment).
- **`@tailwind components`**: Loads Tailwind's component classes.
- **`@tailwind utilities`**: Adds Tailwind's utility classes, which is the framework’s bread and butter for building responsive, utility-first UIs.

---

### Reset Styles with Preflight

Once you’ve imported the base styles, Tailwind automatically applies its Preflight styles—a modernized reset based on Normalize.css—to address common cross-browser inconsistencies.

Here’s what Preflight does to clean up the default browser styling:

1. Removes default margins from elements like headings, paragraphs, and lists.
2. Unstyles headings (h1, h2, etc.), so they have the same font size and weight as normal text.
3. Removes decorations, margins, and paddings from ordered and unordered lists.
4. Ensures elements like img, svg, video, canvas, etc. are block-level and fit within their parent containers.
5. Makes images responsive by default, constraining their width to the parent while maintaining aspect ratio.
6. Resets global border styles to ensure consistency.

You can find more detailed info on Tailwind's Preflight here.

---

#### Disable Preflight (Optional)

If you’d rather use your own base styles or a different reset strategy, you can easily disable Preflight. Add this configuration to your `tailwind.config.ts`:

```ts
  module.exports = {
    corePlugins: {
      preflight: false,
    }
  }
  ```

This will prevent Tailwind from injecting its base styles into your project, giving you complete control over the initial look of elements.

## Define Your Foundations

Now that you've loaded either the default reset stylesheet Preflight or configured your own, it's time to define the base styles of your design system.

The foundational elements of a design system tend to be composed of the following sections:

1. Colors
   - **Primary Colors**: Main colors representing the brand; typically one or two.
   - **Secondary Colors**: Complementary colors meant to balance primary colors.
   - **Tertiary/Accent Colors**: Supporting colors used for details like alerts or links.
   - **Neutrals**: Grays, whites, and blacks used for backgrounds, borders, and text.
   - **Status Colors**: Colors that indicate states like success (green), error (red), and warning (yellow).
    ```ts

    const colors = {
      primary: '#1a73e8',
      secondary: '#34a853',
      error: '#d93025',
      success: '#34a853',
      warning: '#fbbc05',
      neutral: {
        light: '#f8f9fa',
        medium: '#e0e0e0',
        dark: '#3c4043',
      },
    };

    ```
2. Typography
   - **Font Families**: Set of fonts approved for use within the application.
   - **Font Weights**: Boldness variations (e.g. regular, bold, extra-bold).
   - **Font Sizs**: Sizes for headings (`h1`-`h6`), body text, and captions.
   - **Line Height**: Spacing between lines.
   - **Letter Spacing** Adjustments to spacing between characters.
    ```ts

    const typography = {
      fontFamily: `'Inter', sans-serif`,
      fontSizes: {
        h1: '48px',
        body: '16px',
      },
      lineHeight: {
        h1: '56px',
        body: '24px',
      },
      letterSpacing: {
        normal: '0.02em',
        wide: '0.05em',
      },
    };

    ```
3. Spacing & Layout
   - **Spacing Scale**: Defines the standard space between elements (e.g. `4px`, `8px`).
   - **Grids**: Layout system for structuring content.
   - **Breakpoints**: Media query breakpoints for responsive design.
   - **Container Widths**: Define maximum widths for content areas.

### Dynamically Generate CSS Variables Using SCSS Mixins

Mixins allow you to write reusable chunks of CSS, making your code **DRY (Don't Repeat Yourself)** and scalable. In this case, you can use SCSS mixins to **dynamically apply colors** to different sections and components.

#### Why Use Mixins for Colors?

Mixins let you define reusable styles that can accept **parameters**. In this case, my mixins take in color variables for each section, allowing me to set both primary and secondary color schemes consistently across components.

Here's why it's useful:

1. **Reusability**: The mixin can be applied anywhere, so I don’t need to redefine color rules for each section.
2. **Flexibility**: Mixins allow me to dynamically pass different values (in this case, color variables) when applying styles, making it easy to switch color schemes across multiple sections.

**Example**: Below, I’ve created mixins that apply the color variables defined earlier as CSS variables to each section.

<CodeFolding>

```scss

@mixin create-color-vars($section, $primary, $secondary) {
  :root {
    --#{$section}-50: #{list.nth($primary, 1)};
    --#{$section}-100: #{list.nth($primary, 2)};
      ...
    --#{$section}-950: #{list.nth($primary, 11)};
  }
  [data-id='#{$section}'] {
    // Primary Shades
    --primary-50: #{list.nth($primary, 1)};
    --primary-100: #{list.nth($primary, 2)};
      ...
    --primary-950: #{list.nth($primary, 11)};

    // Secondary Shades
    --secondary-50: #{list.nth($secondary, 1)};
    --secondary-100: #{list.nth($secondary, 2)};
      ...
    --secondary-950: #{list.nth($secondary, 11)};
  }
}

@mixin create-single-color-vars($section, $color) {
  :root {
    --#{$section}-50: #{list.nth($color, 1)};
    --#{$section}-100: #{list.nth($color, 2)};
      ...
    --#{$section}-950: #{list.nth($color, 11)};
  }
}

// Apply mixins to sections
@include create-color-vars('hero', $hero, $about);
@include create-color-vars('about', $about, $skills);
@include create-color-vars('skills', $skills, $experience);
  ...
@include create-color-vars('education', $education, $neutral);
@include create-single-color-vars('neutral', $neutral);

```

</CodeFolding>

#### How It Works

- **Mixin Structure**: The mixin accepts three parameters: `$section`, `$primary`, and `$secondary`.
  - **`$section`**: Defines the section the color applies to.
  - **`$primary`** and **`$secondary`**: Define the primary and secondary color schemes for that section.
- **Root Variables**: Inside the mixin, SCSS’s `list.nth()` function is used to access specific shades from the color list and assign them as CSS variables.
  - These variables can then be applied dynamically throughout the sections.
- **Scoped Variables**: The `data-id` attribute scopes the color variables to a specific section, ensuring that every section gets its own unique primary and secondary color variables without overlap.

#### Breakdown

**Root-Level Variables**: Global variables are applied via `:root` to maintain consistency across the entire app.

**Section-Specific Variables**: Variables are scoped to specific sections using the data-id attribute, which allows each section to have its own colors without conflicts or unintended overrides.

**Dynamic Application**: The mixin dynamically generates CSS variables based on the parameters passed. This makes it easy to update the color scheme for any section simply by modifying the variable values.

## Leveraging Tailwind Plugins for Extended Functionality

One of the reasons I kept falling back on custom CSS and SCSS was because I needed functionality that Tailwind didn’t offer out of the box. In the early stages, I’d completely overlooked Tailwind’s plugin system, and by the time I realized, I was already knee-deep in unnecessary custom styles.

By integrating Tailwind's plugin system into my workflow, I’m now able to cut down on the amount of custom CSS needed while extending Tailwind’s capabilities, ensuring a more consistent and maintainable approach to styling across the site. Here’s a breakdown of the plugins I’m using to clean up my project.

<Callout>

**The Power of Tailwind Plugins**
Tailwind’s plugin system is often overlooked. By leveraging plugins like Typography, Forms, and Aspect Ratio, you can extend Tailwind’s core functionality and reduce the need for custom CSS, keeping your styles lean and consistent.

</Callout>

### Plugins I’m Using

#### 1. Typography

The Typography plugin adds built-in typographic utilities, making it much easier to style text-heavy content like blog posts or case studies—without having to resort to custom CSS.

I’m already using this plugin in key sections of my portfolio, such as /blog and /projects. However, as I move forward, my goal is to ensure the entire site follows a more consistent typographic style, reducing the scattered custom overrides that crept in during development.

To install:

```bash
  npm install @tailwindcss/typography
  ```
Add it to your Tailwind config:

```bash
  module.exports = {
    plugins: [require('@tailwindcss/typography')],  
  }
  ```

#### 2. Forms

Forms are notoriously tricky to standardize across a project, and I’ve noticed discrepancies in styling `button`s, `input`s, and `checkbox`es. Enter the Forms plugin, which simplifies and unifies the styling for all form-related elements. Instead of custom CSS overrides across different sections and type safety errors across use cases, this plugin ensures consistency across the board.

To install:

```bash
  npm install @tailwindcss/forms
  ```

Add it to your Tailwind config:

```bash
module.exports = {
    plugins: [require('@tailwindcss/forms')],
  }
  ```

While I haven’t used this plugin extensively yet, I’m looking forward to seeing how it helps me **standardize form controls**, especially as I start refining interactive elements across the site.

#### 3. Aspect Ratio

This plugin is a great alternative to native aspect-ratio support, particularly for older browsers. It provides utility classes like `aspect-w-*` and `aspect-h-*`, allowing you to set fixed aspect ratios without having to manually calculate dimensions. Perfect for videos, images, or anything that needs to maintain a specific aspect ratio across different devices.

For example, I can easily apply an aspect ratio to images like this:

```tsx

<div className="aspect-w-16 aspect-h-9">
  <Image {...props} />
</div>

```

This keeps the dimensions under control, regardless of the screen size.

#### 4. Container Queries

One of the more recent additions to the Tailwind plugins system is the **Container Queries** plugin. Instead of styling elements based solely on the viewport width (traditional media queries), container queries let you apply styles based on the size of the parent container. This gives you far more control, especially when building reusable components that might live in varying layouts.

With this plugin, you can use variants like `@sm` and `@md` based on the container dimensions rather than the viewport:

```tsx

<div className="@container">
  <div className="@lg:text-sky-400">{...}</div>
</div>

```

This allows me to adapt content within dynamic layouts while keeping everything scalable and modular—especially useful for responsive components inside grids or flexible containers.

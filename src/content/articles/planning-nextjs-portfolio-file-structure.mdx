## Introduction

In this tutorial, I'll walk you through building a portfolio site from scratch using Next.js 14, TypeScript, and TailwindCSS. Whether you're new to these technologies or looking to refresh your skills, by the end of this guide, you'll hopefully a solid foundation and understanding of how to set up and configure these tools to build a performant and scalable application.

### What is Next.js?

Next.js is a React-based framework that simplifies the development of web applications. It offers powerful features like **server-side rendering (SSR)**, **static site generation (SSG)**, and **incremental static regeneration (ISR)**, making it the perfect choice for building dynamic, optimized, and scalable websites.

Next.js also provides built-in routing and API capabilities, making it a full-stack solution that works seamlessly with React. With the newest update, Next.js 14, we also now have enhanced features like **App Router**, parallel routes, and server actions, making it even easier to manage your application’s structure and performance.

### What is TypeScript?

TypeScript is a **superset of JavaScript** that adds static types, allowing you to catch potential errors during development rather than at runtime. By using TypeScript in a Next.js project, you get the benefits of type checking, better tooling (like IntelliSense in your code editor), and improved code maintainability.

In this guide, I'm opting for TypeScript to take full advantage of its features while building my portfolio, making it easier to scale and debug in the future.

### What is TailwindCSS?

TailwindCSS is a utility-first CSS framework that allows you to build custom designs quickly by applying predefined classes directly in your HTML. Unlike traditional CSS frameworks that come with predefined components, Tailwind allows you to create your own components without having to fight against a predefined style system.

It integrates well with Next.js and TypeScript, so that you can build highly customizable, responsive designs that are easy to maintain. Tailwind also helps keep your CSS footprint small, thanks to its **JIT (Just-In-Time)** engine that generates only the styles you use in your project.

## Installation

### Create Your Next.js App

To get started, use the following command to initialize your project with `create-next-app`, which includes default configuration files and an optimized setup:

```md
npx create-next-app@latest
```

You'll be prompted with a series of questions. Let’s break each one down:

#### Project Name

```md
What is your project name?
```

This is pretty straightforward. Your input here will name the folder that hosts your app, and Next.js will use this name in various parts of your configuration. Don't stress too much about it, though—you can change it later, and you can easily connect it to any GitHub repository, regardless of the project’s folder name.

If you don't enter a name, it will be created using the default name `my-app`.

#### TypeScript Setup

```md
Would you like to use TypeScript? No / Yes
```

**TypeScript** is highly recommended because of the benefits it provides in catching bugs early and making your codebase easier to maintain. If you're new to TypeScript, don’t worry—Next.js makes integrating it seamless. Choosing 'Yes' will automatically set up TypeScript, and you’ll find a `tsconfig.json` file generated for you.

#### ESLint Configuration

```md
Would you like to use ESLint? No / Yes
```

**ESLint** is a tool to enforce coding standards and help you avoid errors in your JavaScript/TypeScript code. It integrates well with Next.js and can help you maintain consistent and error-free code. If you're working in a team or plan to scale the project, ESLint is essential. Even if you’re a solo developer, it’s worth using to keep things clean.

#### TailwindCSS Setup

```md
Would you like to use TailwindCSS? No / Yes
```

Selecting **'Yes'** here saves you time by automatically configuring **TailwindCSS** for you. If you’d prefer to configure your styling manually, Next.js supports a variety of CSS options including:

- CSS Modules
- SASS/SCSS/LESS
- Pure CSS

However, in this guide, we’ll use TailwindCSS because of its simplicity, flexibility, and ease of building responsive, modern UIs.

#### `src/` Directory

```md
Would you like your code inside a `src/` directory? No / Yes
```

This question asks if you want your project files to be placed under a `src/` folder for better organization. It's not mandatory, but it’s considered a best practice in larger projects because it helps separate application logic from configuration files and utilities. If you're starting from scratch, I recommend selecting 'Yes' for a cleaner project structure.

#### App Router

```md
Would you like to use App Router? (recommended) No / Yes
```

With Next.js 14, the **App Router** simplifies routing and layouts with new features like nested layouts, intercepting routes, and parallel routes. It’s the new standard for Next.js projects, and I highly recommend enabling it. This guide assumes you’ll be using the App Router, so choose 'Yes' here.

#### Import Alias

```md
Would you like to customize the import alias (`@/*` by default)? No / Yes
```

Next.js uses the `@/*` alias by default for absolute imports from the root of your project. You can customize this alias if needed, but for most projects, sticking with `@/*` is enough and helps keep things simple.

### Manual Installation (Optional)

If you prefer more finegrained control over your setup or you’re upgrading an existing project, you also have the option of manually installing Next.js, TypeScript, and TailwindCSS.

To do this, follow these steps:

1. Install Next.js:
    ```md

    npm install next react react-dom

    ```
2. Install TypeScript and the required type definitions:
    ```md

    npm install typescript @types/react @types/node --save-dev

    ```
3. Create a tsconfig.json file:
    ```md

    npx tsc --init

    ```
4. Install TailwindCSS:
    ```md

    npm install tailwindcss postcss autoprefixer

    ```
5. Initialize Tailwind:
    ```md

    npx tailwindcss init

    ```
6. Configure your Tailwind and PostCSS:
    - Add the following to tailwind.config.js:
    ```js
    module.exports = {
      content: ['./pages/**/*.{ts,tsx}', './components/**/*.{ts,tsx}'],
      theme: {
        extend: {},
      },
      plugins: [],
    };
    ```
7. Include Tailwind in your global CSS file (globals.css):
    ```css

    @tailwind base;
    @tailwind components;
    @tailwind utilities;

    ```

Now you have manually installed Next.js, TypeScript, and TailwindCSS, allowing you more control over your setup.

Follow the official instructions in the [Next.js documentation](https://nextjs.org/docs/getting-started/installation) for more information on how to customize your setup.

Let’s break down each folder and file to understand its purpose.

### `node_modules/`

This directory contains all the project dependencies installed via `npm` or `yarn`. You typically don't need to worry about this folder -- it's generated automatically when you install packages.

Thanks to `.gitignore`, it's always ignored in version control as well!

### `src/`

This is where all your application code lives, if you opted for the `src/` directory structure from the initial prompts. Next.js places all the core parts of your app here. To start, you should find the following files and folders:

#### `app/`

This folder contains the main logic for your app, including page components and layouts.

##### `layout.tsx`

This file acts as a wrapper for your pages. It's where you can define global components like headers (including elements like navbars) or footers that persist across all routes.

Think of this component as a consistent layout shared across your pages. You should avoid including code that depends on logic or anything data-related (like fetching from a server); this component should only be used for basic UI definitions that will wrap all other `page.tsx` and `layout.tsx` files below it within the folder directory.

This is also where you host meta information that should persist across different pages.

<CodeFolding>

```tsx

  import type { Metadata } from "next";
  import localFont from "next/font/local";
  import "./globals.css";

  const geistSans = localFont({
    src: "./fonts/GeistVF.woff",
    variable: "--font-geist-sans",
    weight: "100 900",
  });
  const geistMono = localFont({
    src: "./fonts/GeistMonoVF.woff",
    variable: "--font-geist-mono",
    weight: "100 900",
  });

  export const metadata: Metadata = {
    title: "Create Next App",
    description: "Generated by create next app",
  };

  export default function RootLayout({
    children,
  }: Readonly<{
    children: React.ReactNode;
  }>) {
    return (
      <html lang="en">
        <body
          className={`${geistSans.variable} ${geistMono.variable} antialiased`}
        >
          {children}
        </body>
      </html>
    );
  }

```

</CodeFolding>

**Breakdown**:

- **Imports**:
  - The `Metadata` type is imported to define metadata like title and description, which will be useful for SEO.
  - The `localFont` function is used to load fonts from the `/fonts` folder locally. `geistSans` and `geistMono` are examples of variable fonts being loaded.
- **Metadata Object**:
  - This object holds the metadata for the entire app. In this example, it sets the title (`Create Next App`) and description (`Generated by create next app`).
- **RootLayout Component**:
  - The layout wraps all pages with an `<html>` tag and sets the language attribute to English (`lang="en"`). The `body` tag uses the `geistSans` and `geistMono` font variables to apply custom fonts.
  - The `children` prop allows all nested page components to render within this layout.

This folder is typically where you can store custom fonts. If you want to import a local font (as opposed to using a web font), you can add it here and use Next.js's `next/font` API to load it automatically in your project.

This file is the default favicon for your website. You can replace it with your own custom favicon to make your site stand out in browser tabs.

#### `globals.css`

This file is where your global styles live. By default, when you use TailwindCSS, this is where the core Tailwind utilities are imported, such as:

```css

@tailwind base;
@tailwind components;
@tailwind utilities;

```

Without these initial utilities imported, you won’t be able to use TailwindCSS in your project. You can also define global CSS variables or resets here.

<CodeFolding>

```css

@tailwind base;
@tailwind components;
@tailwind utilities;

:root {
  --background: #ffffff;
  --foreground: #171717;
}

  :root {
    --background: #0a0a0a;
    --foreground: #ededed;
  }
}

  color: var(--foreground);
  background: var(--background);
  font-family: Arial, Helvetica, sans-serif;
}

@layer utilities {
  .text-balance {
    text-wrap: balance;
  }
}

```

</CodeFolding>

**Breakdown**:

- **CSS Variables**: Global CSS variables for background and foreground colors are defined here, and they change based on the user’s preferred color scheme (light or dark mode).
- **Custom Utility (`@layer utilities`)**: A custom utility class `.text-balance` is defined, allowing for text wrapping with better balance.

## Crafting My Portfolio File Structure

Now that we’ve covered the basics of the project setup, let’s dive into how I approached organizing the file structure for my **portfolio rebuild**.

In my original build, I experimented with different ways of structuring the files. Initially, I had a dedicated `components` folder inside `src`, which contained a `shared` folder for reusable components like `BaseButton`, `IconButton`, `FlipCard`, and so on. I also had separate folders for each section like **About**, **Skills**, and **Projects**.

However, this approach became confusing as I found myself duplicating components across different sections and often having to rebuild elements that could have been reused.

<CodeFolding>

```md

  src/
    app/
      page.tsx
      layout.tsx
    components/
      shared/
        BaseButton/
        Icon/
        ImageComponent/
        Input/
        FlipCard/
        Overlay/
        VideoComponent/
      About/
        AboutContainer/
        AboutItemCard/
        AboutCardFront/
        AboutCardBack/

```

</CodeFolding>

This separation made sense in theory, but as the project grew, it became harder to manage. I ended up with a tangled mess where related files were scattered across different directories.

Eventually, I tried colocating the `components` folders within each section under `app` while keeping reusable components like buttons and cards under `shared`.

<CodeFolding>

```md

  src/
    components/
      mdx/
        IconButton/
        Heading/
        List/
      shared/
        BaseButton/
        IconButton/
        Icon/
        Input/
        FlipCard/
        ImageComponent/
    app/
      (content)/
        blog/
          ArticlesContainer/
          ArticlesGrid/
          ArticlesCard/

          components/
            ProjectContainer/
            ProjectCard/
            ProjectSkillCard/
      skills/
        components/
          SkillContainer/
          SkillList/
          SkillCard/
      page.tsx
      layout.tsx
      
```

</CodeFolding>

While this was an improvement, it still felt too fragmented. The split between the `components` folder and `app` created confusion. I realized I needed a more intentional structure, where components and logic were clearly grouped by their purpose while allowing for reusability.

### Final File Structure

After much trial and error, I refined the structure to balance component reuse with logical separation. I organized components under `components/` based on their purpose (like **cards**, **media**, **buttons**), and grouped page-specific logic under `sections/` within `app/`. This way, shared components live in a central place, while page-level components remain colocated within their respective sections.

<CodeFolding>

```md

    app/
      (content)/
        blog/
          [slug]/
          components/
            ArticleContainer/
            ArticleGrid/
          layout.tsx
          page.tsx
        projects/
          [id]/
          components/
            ProjectContainer/
            ProjectGrid/
          layout.tsx
          page.tsx
        mdx/
      sections/
        about/
```

## **Breaking Down the Final Structure**

### **`public/`**

This folder is used to host static files, like images, in which the files can then be referenced by code starting from the base URL (`/`). Normally, this is the folder that would host your images, icons, fonts, as well as static metadata files, such as `robots.txt`, `favicon.io`, etc.

However, Next.js cannot safely cache assets within this folder in the event they may change; only assets in the directory at build time will be served while any files added at request time won't be available.

I'm already planning to handle my fonts using Next.js's font system, which supports self-hosting, and using Vercel Blob to host my static assets, such as images and videos. While these optimizations definitely reduce the need for a `public/` folder, there are still a few potential use cases that make sense.

```md

  node_modules/
  public/
    metadata/
      robots.txt
      sitemap.xml
      favicon.ico
      apple-touch-icon.png
    images/
      og-image.png
    docs/
      Hanaa_Sadoqi_Resume.pdf
  src/
  package-lock.json
  package.json
  next.config.mjs
  tsconfig.json

```

#### Use Cases

1. **Favicon and Metadata Assets**
   While my metadata will be handled within either individual routes or layouts under the `app/` folder, it is still a good idea  to store static assets used for SEO or social sharing within `public/`.
   ```md
    public/
      |-- favicon.ico
      |-- robots.txt
      |-- sitemap.xml
      |-- apple-touch-icon.png
   ```
2. **Static Downloads**
   For files that you intend users to download directly, use this directory to host those files. This is especially useful if you need the file to be easily downloadable via a static URL (e.g. `/hanaa_sadoqi_resume.pdf`).
   - Other potential files include PDFs, terms of service, privacy policy documents, etc.
3. **Custom Static Assets**
   Despite using Vercel Blob, there are cases in which static assets should be served directly and are therefore hosted within this folder.
   - Examples include icon sets, documents, etc.
   - You may also choose to statically host images such as **custom Open Graph images** under `public/` and access them directly in your metadata:
    ```ts
    export const metadata: Metadata = {
      title: "My App",
      description: "My App's soooo cool",
      openGraph: {
        images: [
          {
            url: "/images/og-image.png",
          }
        ]
      }
    }
    ```

#### Fonts

The new font system, supported by `next/font`, will automatically optimize your fonts with **built-in automatic self-hosting**. Files for web fonts will be downloaded at build time with the rest of the static assets, without sending any requests from the browser.  

The fonts will be preloaded on the `page` or `layout` on which it is defined so that it is either available on the unique route for that page or globally availale on all the routes wrapped by the layout.

To load the same font in multiple files, rather than initialize different instances of the same fonts to be hosted on multiple routes, it is recommended to use a font loader function and reuse the constant wherever it is needed.

For argument's sake and because I'm not sure how much I'd like to scale my portfolio in the future, I've decided to host them under `src/styles/fonts`in a font definitions file.

<CodeFolding>

```ts

  subsets: ['latin'],
  display: 'swap',
  variable: '--font-poppins',
  weight: ['400', '500', '600', '700', '800'],
})

export const raleway = Raleway({
  subsets: ['latin'],
  display: 'swap',
  variable: '--font-raleway',
  weight: ['400', '500', '700'],

  subsets: ['latin'],

  children

  )
}
```

### Imports

And finally, don't forget to update the paths within `tsconfig.json` to keep your project maintainable and avoid deep relative imports (e.g. `../../../styles`):

```json

  "paths": {
      "@/*": ["./src/*"],
      "@/sections/*": ["./src/app/sections/*"],
      "@/styles/*": ["./src/styles/*"],
      "@/font/*s": ["./src/styles/fonts/*"],
      "@/components/*": ["./src/components/*"],
```
